## 做了什么

- `clip` 新增两组命令，都走窗口同一套代码：
  - `clip shortcut list | scope <动作> application|global | clear <动作>|--all`：设置 → 快捷键 的查看、作用范围、清除。走 `ClipShortcuts`，沿用窗口的校验。命令不新增组合键，录制仍要本人在窗口里按键；默认绑定仍为空。
  - `clip config status | export -o <file> | import <file> --yes | sync on|off --yes`：「配置与更新」窗口的开关状态、导出、导入、iCloud 记住配置。走共享的 `AppConfiguration`；键清单收到 `ClipPortableConfiguration`，窗口与命令共用一份。
- 运行中的 App 收到偏好变更信号时多做一步 `shortcuts.reload()`；新增两条信号让 App 拨「使用 iCloud 记住配置」。
- 顶层 `clip --help` 补齐四样：读 / 写命令分组、`--json` 成功与失败的形状和短码、退出码表、「仅在窗口中」清单。已有命令的 JSON 结构没有改。
- `project.yaml` 写了 `sop.agent_cli`（读回 `clip status`）。
- 手机端 `ios/01-源程序/project.yaml`：`sop.cli` 指到 Mac 端的 `clip`（`app: cyou.tianli.clipbook`），并写了手机端的 `sop.agent_cli`（读回 `clip cloud status`）。

### 共享层的隐患：实测与修法

核验指出 `AppLifecycleCLI.follow()` 在运行中的 App 里收到通知 0.3 秒后会执行 `setEnabled(configuration.enabled)`，App 读到旧值时会把命令刚拨的开关写回去。

- 实测办法：共享测试 `test_app_lifecycle_cli.py` 把夹具起成第二个无窗口进程充当运行中的 App（同一个 `AppConfiguration`、产品要加的那一行 `follow`、一个 run loop；没有 NSApplication、不上屏、不进 Dock），命令进程经私有通道拨开关。全程用一次性偏好域、临时支持目录与「云」目录，没有碰本人的 iCloud 配置。
- 旧写法：`--measure-legacy` 测了 20 次开关，以另起进程读到的存储值为准，回退 0 次。隐患是时间窗口而不是必现：0.3 秒的等待在这台机器上盖住了偏好到达的延迟。
- 修法（共享模块，只动 `AppLifecycleCLI.swift`，三份原版字节未变）：命令在通知里带上它把开关拨到了哪边（`sync=on` / `sync=off`），App 把这个值交给窗口同一条路径，不再重放自己读到的值；导入不带开关状态，App 只重读设置。新写法 3 轮开、关都跟随且保持，导入后 App 读到新值，共 60 项检查通过。
- casesift、initials 的 `vendor-lifecycle.py --check` 仍通过；除 Clip 外没有产品持有 `AppLifecycleCLI.swift`。修法与「产品已有 config 命令时怎么接」写进了 app 技能 `references/platforms.md`。

### 共用层 AppConfiguration 的一个发现（没有改，只留证据）

「使用 iCloud 记住配置」开着时，同一项设置在一次同步还没跑完时又改了一次，后一次的值会在下一次同步时被写回成前一次的值。

- 探针：只编总部的 `AppConfiguration.swift`（sha256 66d1b040…，Clip 的副本与它相同）加一个主程序，隔离的支持目录与云端目录、一次性偏好域，只用生产的触发（同一个 `UserDefaults` 对象上的 `didChangeNotification`），不手动调 `reconcile()`。每轮把一个键连改两次，等 0.25 秒，再改另一个键（充当下一次同步），等 0.25 秒，读第一个键。
- 结果一（每档 40 轮）：两次改动间隔 0 微秒，后一次的值丢 0 轮；间隔 300、1000、3000 微秒，分别丢 30、34、35 轮；间隔 60 毫秒，丢 0 轮。
- 结果二（每档 30 轮）：间隔 0 微秒丢 0 轮；间隔 1000 微秒丢 29 轮，29 轮都是变回前一次的值，期间同步写回设置（留下备份）正好 29 次；间隔 60 毫秒丢 0 轮；同步关着、间隔 1000 微秒，丢 0 轮。连改两次之后不再改别的设置，0.25 秒后看：本机已经变回前一次的值 0 轮；本机是后一次的值而云端副本停在前一次的值 25 轮；两边都是后一次的值 5 轮。也就是先出现「云端落后一步」，到下一次同步才把本机写回去。
- 读源码的解释（没有单独做实验隔离）：`reconcile()` 开头取一次本机快照去合并和写云端，写完再取一次快照记成基线的「本机」一侧（`writeState(local: applied, cloud: merged)`）。两次快照之间设置变了，基线就成了「本机是新值、云端是旧值」；下一次同步看到本机相对基线没变，按合并规则取云端的旧值写回本机。
- 对 Clip 的含义：只在配置同步开着时。两条 `clip settings set` 背靠背间隔几十毫秒，隔离目录下一次同步只要几毫秒，碰不上；真实 iCloud Drive 上一次同步要多久没有测，慢到几十毫秒就会碰上。窗口里拖音量滑块这类连续改动更容易碰上。别的持有这份共用文件的产品同理。
