# Clip：截图、录屏、OCR 与剪贴板统一应用 PRD

日期：2026-10-05。状态：需求与设计阶段；本轮仅写文档，新增功能尚未实现。

## 用户要求

用户明确仍需要 CleanShot X、Deck、TextSniper，要求了解功能后合成自己的一个 App，先写 PRD，再切到对应目录实施。三款现有工具继续保留。

方案落在 **`~/Apps/clip/mac` 现有原生 Clip 项目**。该项目已经具备剪贴板记录、搜索、编辑、转换、Deck 历史导入、CLI 与可选 iCloud，适合承接统一工作流。名称、应用身份、历史路径、用户快捷键保持连续。

目标：捕获一次，即可识别、标注、整理和复用；共用数据、缓存、OCR 和复制动作，减少重复常驻资源。完整替代前，录屏、长截图等需求不能因“合并”而丢失。

## 已核实的功能归属

官方公开能力于 2026-10-05 核对，未逐项实测本机安装版本。

| 产品 | 主要职责 | 合并安排 |
|---|---|---|
| [CleanShot X](https://cleanshot.com/features) | 截图、长截图、标注、贴图、录屏、OCR、捕获历史 | 新增捕获与编辑工作流 |
| [Deck](https://github.com/yuzeguitarist/Deck) | 多类型剪贴板历史、搜索、分类、模板、转换、自动化 | 复用 Clip，按差距增补 |
| [TextSniper](https://www.textsniper.app/) | 框选取字、二维码 / 条码、朗读 | 共用按需 OCR 和文本动作 |

重叠主要在 OCR、图片历史和复制：原图保存一份，识别一次，文本关联原图；结果可以直接复制、编辑、导出或归档。

本机一次诊断读到三者约 148 / 110 / 36 MiB。这只是诊断快照，不是公平空闲基准；应用计账也不能直接当作物理 RAM 释放量。不能据此承诺整机内存从约 10 GiB 降到 8 GiB 以下。

## 主要使用流程

1. **截图分享**：选区域 / 窗口 → 结果浮层 → 标注或遮盖 → 复制 / 保存 / 拖出；取消不写库、不改剪贴板。
2. **屏幕取字**：进入识别模式 → 框选 → 本机 OCR → 预览修正 → 复制；支持保留或去除换行，不默认粘贴到其他应用。
3. **复用历史**：按来源、类型、关键词找内容 → 预览 / 编辑 → 复制或粘贴；图片可直接取字，结果关联原条目。
4. **录制演示**：选内容与音源 → 倒计时 → 录制 / 暂停 / 恢复 → 停止并完成文件 → 预览、裁剪、导出。
5. **保存长内容**：选滚动区域 → 逐段捕获和拼接预览 → 停止 / 修正 → 导出；到底、重复帧和超限有明确状态。

保留 Clip 的正常独立应用形态：Dock、⌘Tab、应用菜单与主窗口；菜单栏作为附加入口。捕获、编辑和识别窗口按需创建，关闭后释放。

## 模块与数据

- 沿用 `ClipStore`、`Classifier`、`ClipActions`、`ClipCopy`、`Paster`、`DeckImporter` 和 `AppSettings`；GUI / CLI 共用动作、校验和业务判据。
- 新增捕获服务、按需 OCR、图像编辑文档、录制状态机和媒体索引。单张捕获只存一份原图，OCR 按内容哈希、参数和引擎版本缓存，识别文本关联原条目。
- 保留旧条目 ID 和迁移路径；新媒体类型、OCR 索引、编辑项目通过版本化迁移加入，非破坏性编辑与导出分开。
- 视频写磁盘，库只存文件引用和有界预览；不把整段录屏塞进 SQLite BLOB。录屏默认不进入现有图片 iCloud 归档，媒体同步另设大小与保留策略。
- 主动捕获、保存和复制分开，沿现有来源标记避免 watcher 再入库。暂停历史采集时仍允许用户手动截图 / OCR，保存由当前动作决定。

技术优先采用系统框架：[ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit) 做屏幕与音频捕获，[Vision](https://developer.apple.com/documentation/vision/vnrecognizetextrequest) 做本机 OCR，AppKit / Core Graphics 做编辑，AVFoundation 做编码。保持 macOS 14 基线，新系统接口做 availability 分支，麦克风路径单独核验。

实现从已有 Clip 和系统框架出发。[Deck 许可证](https://github.com/yuzeguitarist/Deck/blob/main/LICENSE) 将 GUI 等目录列为 All Rights Reserved，只有 `deckclip/` 为 AGPL；本方案不复制其 GUI 源码或商业产品资源。

## CLI、权限与快捷键

以下是拟新增入口，**尚未实现**：

```text
clip capture area|window|display ... --json
clip ocr --file <图片> --json
clip ocr --item <ID> --json
clip record start|pause|resume|stop|status ... --json
clip media export <ID> --output <路径> --json
```

读状态不建窗口、不改偏好、不申请权限。复制结果需显式 `--copy`；录制命令交给同一运行中 App，不起第二个录制器。交互区域选择如实要求捕获界面，不能假装无界面。

屏幕录制、麦克风、辅助功能按动作分别请求，拒绝时说明状态与可用路径。默认零全局快捷键；用户保存才注册，不绑定 `⌘⇧V` 或接管 Keyboard Maestro 宏。测试使用隔离库、偏好与命名剪贴板。

## 资源预算

以下是验收目标，尚未实测通过；计入 App 自有辅助进程。

| 场景 | 初始预算 / 测法 |
|---|---|
| 空闲、主窗口关闭、无同步 / 录制 | `phys_footprint` 峰值 ≤80 MiB；静置 45 秒后采样 60 秒；CPU 平均 ≤0.2%，100% 为一个核心 |
| 一批截图 / OCR 后回到空闲 | 60 秒内 ≤100 MiB，不保留屏幕帧、解码副本和 OCR 队列 |
| 1080p / 30 fps 录制 | 初始稳态 ≤256 MiB；有界帧队列；连续 30 分钟检查内存斜率、丢帧和音画同步 |
| 大图编辑 / 长截图 | 有像素上限、内存估计、取消和落盘；采用分块处理，不无限积累原始帧 |
| 历史与重复调用 | 10,000 条样本；连续 100 次捕获 / OCR 后复测，不随图片数长期线性增长 |

空闲不运行录屏流、不扫全部历史做 OCR、不预载原图。OCR 初始并发 1，只按请求或明确开启的新增图片规则执行；隐藏窗口沿现有界面卸载和有界缓存机制。优化 0.25 秒 watcher 前先验证连续复制不会漏采。

对比用同一机器、同一库和工作流，分别测三个旧工具与一个 Clip 的应用计账、CPU、延迟、整机 RAM。不能用瞬时诊断直接当公平基准。

## 里程碑与切换

1. 核对现有 Clip 高频流程、Deck 导入、快捷键和真实使用差距，建立隔离样本基线。
2. 完成截图、OCR、编辑、共享 CLI、权限拒绝与取消路径；这一步尚不宣称录屏 / 长截图替代。
3. 完成录屏、长截图、依赖的 P1 能力和资源验收，覆盖捕获、取字、复用与录制全链路。
4. 真实使用通过、历史和设置备份后，经用户确认统一关闭三个旧 App 的常驻 / 自启动，保留可回退安装与数据。PRD 阶段继续保留它们。

实施与交付沿本项目原构建、签名、装机、CLI 和证据流程；设计目标不写成当前版本功能或实测成绩。
